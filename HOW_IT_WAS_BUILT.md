# How the study was built

This page explains how the code is organised and how I used AI to build it. The code itself is private, but I'm happy to walk through it on a call.

## Code architecture

The study is a Python project of about 3,500 lines plus 500 lines of tests. One command, `python src/run_pipeline.py --clean`, rebuilds everything from the saved lap data in about 7 minutes: every result table, every figure and the full report. No number in the report is typed by hand. Every one is read from the results, and a test checks this.

```
regulations.py        every 2026 rule value, with its article and page in the FIA document
model.py              energy model: braking zones, front and rear split, engine, MGU-K
thermal_model.py      rear disc temperature model
        |
01_fetch_telemetry.py     download the lap data once (FastF1), the only step that uses the internet
02_energy_split.py        energy per braking zone, 2025 and 2026
04_sensitivity.py         one input at a time, then 2,000 random combinations
05_thermal.py             disc temperature over the lap, and its uncertainty
06_bias_limit.py          brake balance and MGU-K strategy options
11_joint_ensemble.py      energy and temperature uncertainty together
09_singapore.py           the second track
03, 07, 10                figures
08_report.py              the full report
run_pipeline.py           runs all of the above in order, then the tests
```

**One place for each rule.** Every regulation value lives in `regulations.py`, next to the article, page and a quote from the FIA document. The rest of the code imports it, so a rule can never be typed twice with two different values.

**One place for the MGU-K.** A single function decides how much braking the MGU-K takes, applying the power, torque and energy per lap limits. Every script uses that same function, and a test makes sure no script carries its own copy.

**Results that can be traced.** Every run writes a manifest with, for each output file, the script that made it, a fingerprint of its contents (SHA-256), the random seed and the number of samples. A fixed seed makes every random result repeatable. A clean run first moves all old outputs aside, so an out of date file can never end up in the report.

**Tests.** 65 automatic tests check that the physics and the rules hold. For example: the energy in each braking zone adds up, no energy share is ever negative, no sample goes over 350 kW or 500 Nm or below the minimum mass, more energy recovery can never make the rear brake hotter, less cooling can never make the disc cooler, the same seed always gives the same results, and the report contains no hand typed numbers.

**CAD from the same numbers.** Scripts build the rear corner geometry (disc, bell, caliper and wheel envelopes) and export it as STEP files, reading the disc dimensions straight from the thermal model. A Fusion 360 script sets up the same parameters, so the CAD and the model cannot drift apart. A CFD case matrix for comparing the duct concepts is prepared for the next step.

**Tools:** Python, NumPy, SciPy, pandas, Matplotlib, pytest, FastF1, python-docx, CadQuery, Fusion 360.

All the equations the model uses are written out in [FORMULAS.md](FORMULAS.md).

## How I used AI

I built this study together with an AI coding assistant (Claude, by Anthropic). The assistant wrote most of the Python code. My part was to decide what the study should answer, to tie every rule to the exact article of the regulations, and to question results that did not make sense before accepting them.

We worked by four rules:

1. Every regulation value comes from the FIA document, with its article and page.
2. Anything that is not known is varied over a range instead of guessed, and the result is reported as a range.
3. Assumptions are written down as assumptions, never presented as data.
4. Everything is generated by code and checked by tests, so the report can never drift away from the results.

What I take from this: AI makes it possible to build a study of this size quickly, but the value comes from setting clear rules, checking the output against physics and the regulations, and understanding every step well enough to explain it.
